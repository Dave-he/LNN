# PRD-A — LNN arXiv 目录卫生 + Reproduction Status (round 72)

> **Selected** (round 72, 2026-06-06): 直接对应 deep-research 报告 §2 (arXiv ID 错配) + §4 (复现性), S 难度低风险快闭环, 是 round 73+ LNN 论文工作的前置条件。

## 目标

修正上游 LNN 论文目录中的 arXiv ID 错配 (3 个已确认),并为每条论文元数据增加 `reproduction_status` 字段,让后续 deep-research 流水线和每日 digest 都能在引用前自动校验 "vendor claim" vs "third-party reproduced" vs "failed to reproduce"。

## 用户故事

- As a LNN 研究者, 我希望每个被引用的 arXiv ID 都对应真实论文标题, 这样下游消融实验 / 报告 / 论文综述不会引用到不相关的工作。
- As a 自动化 pipeline, 我希望在 `papers/daily/*.json` 上跑一行 lint 就能发现 ID 错配, 而不必每次都用 deep-research 找问题。
- As a 复现者, 我希望在选定一篇 CfC / LTC 论文做消融时, 能立即看到该论文是否被第三方成功复现, 避免重复踩坑。
- As a 论文综述写作者, 我希望目录自动区分 "vendor claim" (如 CfC 1-5 个数量级加速) vs "诚实反例" (round 24 mackey_glass 6-seed 负结果), 这样能写出更平衡的 review。

## 引擎层职责

| 路径 | 类型 / 方法 | 角色 |
|---|---|---|
| `lnn/core/arxiv_catalog.py` (新) | `class ArxivCatalog` | canonical: 加载 arXiv ID ↔ title/author/abstract 映射 |
| `lnn/core/arxiv_catalog.py` (新) | `def verify_id(arxiv_id) -> VerifyResult` | 调用 arXiv API 反查 title,与目录中的 `title` 字段对比;不匹配返回 mismatch + actual_title |
| `lnn/core/arxiv_catalog.py` (新) | `def add_reproduction_status(arxiv_id, status, repo_url, notes)` | 给每篇加 `reproduction_status ∈ {vendor_claim, third_party_reproduced, failed_to_reproduce, untested}` 字段 |
| `tests/test_arxiv_catalog.py` (新) | 6+ 单测 | 覆盖正常 ID、3 个已知错配 ID (2003.06236, 2203.14343, 2002.08071)、reproduction_status 增改查、重复添加检测 |

## 游戏层职责 (本项目无 game layer, 改为 CLI 层)

## 验收标准

1. ✅ `lnn/core/arxiv_catalog.py` 包含 `ArxivCatalog` 类 + `verify_id` / `add_reproduction_status` 方法, 全部带 docstring 与 type hints
2. ✅ `tests/test_arxiv_catalog.py` 至少 6 个单测, 全部 PASS, 全套 `pytest tests/` 仍 ≥ 137 个零回归
3. ✅ `scripts/lint_arxiv_catalog.py` 可在 dry-run 模式下输出 daily JSON 中所有 ID + 不匹配数
4. ✅ 3 个已知错配 ID (2003.06236, 2203.14343, 2002.08071) 在 lint 报告中明确标红, 并自动给出建议替换
5. ✅ `scripts/show_reproduction_status.py` 输出: vendor_claim 计数 / third_party_reproduced 计数 / failed_to_reproduce 计数 / untested 计数
6. ✅ 在 `papers/daily/2026-06-06_lnn_research.json` 上运行 lint, 至少发现并标注 1 个 ID 错配 (以该文件实际状态为准)

## 实现难度

**S (≤ 2h)**, 分解:
- `arxiv_catalog.py` + 单测: 1h
- 3 个 CLI 脚本: 0.5h
- 在 daily JSON 上跑通 lint + 写报告: 0.5h

## 风险

- **arXiv API 限流**: 单次 lint 可能触发多次 HTTP 请求。需在 `verify_id` 内置 3s 间隔与缓存 (本地 `.arxiv_cache.json`)。
- **ID 错配可能不止 3 个**: deep-research 只抽检了 14 个 claim, 实际 daily JSON 中可能有更多错配。本轮不要求全部修, 只要求 lint 可发现。
- **历史 `papers/daily/*.json` 不应被改写**: 只读扫描, 修正确实错配时单独 commit, 标 `chore(catalog): correct arXiv ID`。
- **reproduction_status 字段为新约定**: 不强制历史 JSON 改写, 只在新 JSON + `arxiv_catalog.py` 中实现。
